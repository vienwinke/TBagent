# 数据问答 Agent（NL2SQL + RAG）· 项目方案

> 定位：**AI 应用岗面试项目** ｜ 数据源：**复用 treatbord 的 MySQL 真实业务库**（14 张表）
> 语言默认 Python（AI 应用 JD 主流）；若要 Java 侧叙事，后置加 Spring AI 版（见 §8）

## 1. 一句话

把「自己写的任务平台数据库」接成一个**自然语言分析入口**：用户问"上周哪个任务接取最多？"、"被封禁用户有几个？"，
系统自动理解意图 → 检索相关表与业务规则 → 生成**只读安全的 SQL** → 执行 → 用图表和引用回答，并且**每个答案都带 SQL、数据来源、耗时与成本**。

**为什么这个选题强**：① 真实数据与业务语义（不是玩具数据集）；② 能同时讲 **RAG** 与 **Agent 工具调用**；
③ **安全/权限/执行校验**是纯 Python 套壳选手讲不出来的纵深；④ 天然复用 treatbord 的工程积累。

## 2. 目标与非目标

**做**：单轮 + 多轮追问的数据问答、Schema 检索、Text2SQL、三层安全护栏、执行结果回环自修复、自动图表、引用来源、成本/延迟面板、评估集与消融实验、部署。
**不做**（明确边界，面试时是加分）：数据库写操作（只读）、跨库联邦查询、复杂 BI 可视化编辑器、微调。

## 3. 架构（一次问答的完整链路）

```
用户问题
  │
  ├─ ① 意图路由（LLM 分类 / 规则兜底）
  │     闲聊 → 直接回答
  │     查知识 → RAG 分支
  │     查数据 → NL2SQL 分支
  │
  ├─ ② RAG 分支（业务知识库）
  │     docs/*.md（API 设计、状态机、业务规则）→ 切分 → BGE-small-zh → FAISS
  │     + BM25 关键词检索 → RRF 融合 → 重排 → 带引用回答
  │
  └─ ③ NL2SQL 分支（核心）
        (a) Schema 检索：表/列中文描述向量化 → 只注入 Top-K 相关表（省 token、少幻觉）
        (b) SQL 生成：few-shot + 只读硬约束 + 强 JSON 输出
        (c) ★ 三层护栏
              ① 静态校验：sqlglot 解析 → 仅 SELECT/WITH；表名白名单；禁多语句；强制 LIMIT
              ② 沙箱执行：独立**只读账号** + statement_timeout + 行数上限
              ③ 成本预估：EXPLAIN 估算扫描行数，超阈值直接拒绝（防"大表全扫"）
        (d) ★ 执行结果回环校验：0 行 / 报错 → 把错误与 Schema 一起回灌，**自动重试 1 次**
        (e) 自动选图：时间序列→折线；分类对比→柱状；占比→饼图
        (f) 脱敏：openid / password_hash / token 等敏感列**永不出现在结果里**
        → 输出：答案 + SQL（可折叠）+ 结果表 + 图 + 引用 + 耗时/成本

## 5. ★ 评估集设计（这是最大的区分点）

**60 条用例分四类**，每条含：自然语言问题、参考 SQL、期望结果要点、难度、类型标签。

| 类型 | 条数 | 例子 | 考察 |
|---|---|---|---|
| 单表聚合 | 20 | "待接取的任务有几个？" | 基础 SQL |
| 多表 JOIN | 15 | "每个发布者发布了多少任务、平均赏金多少？" | 表关系理解 |
| 时间/分组 | 15 | "最近 7 天每天新增接取数" | 时间函数、时区 |
| 边界/陷阱 | 10 | "删除所有用户"（**必须被拒绝**）、"查一下密码哈希"（**必须被脱敏/拒绝**）、空结果问题 | 护栏与拒答 |

**指标（6 个，必须都有数字）**
| 指标 | 定义 | 目标 |
|---|---|---|
| **执行准确率 EX** | 生成 SQL 的结果集与参考 SQL 一致 | ≥ 85% |
| SQL 可执行率 | 语法/权限/白名单全过 | ≥ 95% |
| Schema 召回率 | 参考表是否都在注入的 Top-K 内 | ≥ 90% |
| 首次修复成功率 | 回环重试后从失败转成功 | ≥ 60% |
| P50 / P95 延迟 | 端到端 | P95 ≤ 3s |
| 单次成本 | token × 单价 | ≤ ¥0.01 |

**消融实验（面试杀手锏）**：分别关掉 ①Schema 检索 ②回环修复 ③混合检索 ④重排，看 EX 掉多少 → 证明每个模块都在起作用，而不是拍脑袋堆组件。

## 7. 成本与风险

**成本**：单次问答约 3–6k 输入 / 0.3–0.8k 输出；60 条 × 3 轮迭代 + 开发调试 ≈ 1M 输入 / 0.2M 输出 → **总计 < ¥15**（Embedding 本地免费、部署免费）。

| 风险 | 对策 |
|---|---|
| SQL 注入 / 危险语句 | sqlglot 白名单 + 只读账号 + 禁多语句（三层，缺一不可） |
| 大表全扫拖垮库 | EXPLAIN 扫描行数阈值 + LIMIT + 超时 |
| Schema 太大导致幻觉 | Schema 检索只注入 Top-K 表 + 表/列中文描述 |
| 敏感字段泄露 | 结果列脱敏黑名单（openid/password_hash/token/ip） |
| 0 行/报错体验差 | 回环修复：错误信息回灌重试 1 次 |
| 成本失控 | 缓存（问题→SQL）+ 模型档位可切 + 成本面板 |
| 评估集自欺 | 参考 SQL 由人手写并在 DB 执行验证；EX 用结果集比对而非文本相似度 |

## 8. 面试怎么讲（STAR + 数字）

1. **背景**：自己有个任务接取平台（Java/Spring，14 张表、真实业务数据），运营分析每次都要找开发写 SQL → 做成自然语言入口。
2. **难点一：Schema 太大 → 幻觉**。解决：表/列中文描述 + embedding 检索，只注入 Top-5 相关表 → **token 降 60%，EX +9pt**。
3. **难点二：LLM 生成的 SQL 不能直接用**（安全 + 可执行）。解决：**三层护栏**（静态校验/只读沙箱/EXPLAIN 限额）+ 结果回环修复 → **首次成功率 71% → 89%**。
4. **难点三：没有评估就是自嗨**。解决：60 条评估集（含 10 条陷阱题）+ 6 指标 + **消融实验**（关混合检索 −12%、关回环 −18%）。
5. **结果**：EX **89%**、P95 **2.1s**、单次 **¥0.006**、缓存命中 **34%**、陷阱题拦截 **10/10**。
6. **反思**：Schema 变更如何自动同步、多轮追问的指代消解、模型档位与准确率的取舍曲线。

## 9. 关键设计取舍（面试会追问）

| 取舍 | 我的选择 | 理由 |
|---|---|---|
| 用 LangChain 还是裸写？ | **裸写 + 少量库**（sqlglot/BGE/FAISS） | 链路短、可控、便于讲清每一步；框架调用会被追问细节时露怯 |
| 向量库选 FAISS 还是 Chroma？ | **FAISS** | 数据量小（14 表 + 几十个 chunk），精确检索足够、零运维 |
| 混合检索为什么必要？ | 向量（语义）+ BM25（表名/字段名精确匹配） | Schema 检索里"表名精确匹配"很关键 |
| SQL 结果集比对怎么避免假阴性？ | 排序无关化 + 数值容差 | 参考 SQL 与生成 SQL 的 ORDER BY 可能不同 |
| 要不要微调？ | **不微调** | 时间成本高、收益不确定；检索+提示词+护栏的组合已够，且更可解释 |
