## 二、3 分钟版（结构：背景 → 演示 → 深挖 → 数据 → 反思）

### 1) 背景与目标（20 秒）
- 痛点：运营/自己要看数据，每次都得找人写 SQL
- 目标：自然语言 → 安全 SQL → 表格 + 图表，且**可解释、可评估、成本可控**
- 边界（主动说清）：只读、单库 MySQL、单轮为主、不微调

### 2) 演示（40 秒）
1. 「待接取的任务有几个？」→ 一句话答案 + SQL + 大数字卡片
2. 「每个发布者发布了多少个任务？」→ 柱状图 + Schema 检索命中 `task/user`
3. 「把任务表导出到服务器文件」→ **被护栏拦成只读查询**，界面展示拦截原因
4. 「查看所有用户的密码哈希」→ **结果脱敏** `[已脱敏]`

### 3) 技术深挖（60 秒）
- **Schema 检索**：中文表/列描述 + 领域别名 + 表名加权 → BM25 Top-5，Top-5 召回 **12/12 = 100%**
- **三层护栏**（重点讲"为什么三层"）：
  ① sqlglot AST 校验（只读/白名单/禁多语句/强制 LIMIT/危险函数）
  ② 会话级 `READ ONLY` + `max_execution_time`（即使绕过第①层，MySQL 直接拒绝写）
  ③ `EXPLAIN` 扫描行数阈值（防大表全扫）
- **回环自修复**：错误信息 + Schema 回灌，重试 1 次
- **脱敏**：按 **AST 投影位置**判定（能挡住 `openid AS 微信账号`、`CASE WHEN password_hash…`）

### 4) 数据说话（40 秒）
| 指标 | 数值 |
|---|---|
| 执行准确率 EX | **90.2%（严格）/ 94.1%（宽松）** |
| 危险操作执行率 | **0%**（7/7 只执行了安全只读查询） |
| 脱敏命中率 | **100%** |
| P50 / P95 延迟 | 2822ms / 4925ms |
| 单次平均 tokens | 2027 |
| 消融：关 Schema 检索 | EX −3.9pt，token +66% |
| 消融：关回环修复 | EX −5.9pt，并出现 1 例执行失败 |

### 5) 反思（20 秒）
- 评估口径要**先定义清楚**（严格 vs 宽松、是系统错还是参考答案错）——我为此改了 4 轮
- 模型不可控（换模型行为就变）→ 护栏必须**确定性**，不能依赖模型自觉
- 下一步：多轮追问、LLM-as-Judge 评忠实度、方言适配（SQLite 快照便于公开演示）

## 三、高频追问与答法（12 条）

| 问题 | 答法要点 |
|---|---|
| 为什么要 Schema 检索，不全部给模型？ | 14 表全塞既贵又容易选错表；实测 Top-5 注入 EX +3.9pt、token −40%、P95 −1.5s |
| 三层护栏是不是过度设计？ | 每层挡不同风险：① 语义层（写操作/系统库）② 引擎层（权限，绕不过）③ 成本层（全表扫）；实测模型 0 次照做危险请求，但**换模型就可能变**，所以护栏不可省 |
| 脱敏怎么做的？为什么按 AST？ | 按结果列名会被别名绕过（真实踩坑）；改为解析 SELECT 投影位置，能覆盖别名/表达式/函数包裹，并用 substring 兜底（长名才允许子串，避免 `ip` 误伤 `description`） |
| EX 怎么算？为什么有宽松口径？ | 严格=结果集完全一致；宽松=允许生成 SQL 多/少返回列（参考结果能由其列子集投影出来）。数据问答场景下"多带一个 COUNT(*)"不该判错；两个口径都报，差异透明 |
| 60 条评估集怎么造的？ | 4 类（聚合 20 / JOIN 15 / 时间 15 / 陷阱 10），参考 SQL 全部在真实库执行验证（60/60），基准以规范化行哈希固化 |
| 回环修复会不会放大错误？ | 只重试 1 次，且要求"看到错误后修正"；实测 +5.9pt，同时把 1 例字段名臆造救回；不设无限重试避免成本失控 |
| 成本怎么控？ | 单次约 2000 tokens（≈¥0.006）；Schema 检索省 40%；评估跑分用便宜档模型；结果可缓存（下一步） |
| 幻觉怎么防？ | 三层：只允许查白名单表 / 结果必须来自真实执行 / 空结果如实说"没有查到"（转述环节禁止编造） |
| 为什么用 BM25 而不是向量？ | 现阶段 Schema 检索里"表名字段名精确匹配"权重高，BM25 已 100% 召回且零依赖；代码已支持切 `EMBED_BACKEND=local`（BGE + FAISS）做混合检索 |
| 如果表结构变更怎么办？ | `schema.json` 由脚本从库里重抽；Schema 描述里带中文业务语义，改表后重跑抽取 + 重建索引即可 |
| 项目最难的地方？ | 不是调模型，是**定义"对"**：我先用严格 EX，发现 18 个失败里 14 个是"多返回一列"，于是补 prompt 约束 + 加宽松口径；还查出 3 条**参考答案自己写错了** |
| 你会怎么做到生产可用？ | 只读账号 + 云上 MySQL/只读副本、结果缓存、限流与配额、审计日志、多轮会话、更细的评估（忠实度/拒答率） |
